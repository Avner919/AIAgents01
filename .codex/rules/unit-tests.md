# Правила для тестов

## Область применения

Правила относятся только к репозиторию `C:\Projects\GitHub\AIAgents01` и его подкаталогам. Все относительные пути и команды ниже указаны от корня репозитория.

## Пути

| Назначение | Путь |
| --- | --- |
| Решение | `AIPractice1.slnx` |
| Основной проект | `Exchange/Exchange.csproj` |
| Каталог тестов | `Tests/` |
| Тестовый проект xUnit для .NET 8 | `Tests/Exchange.Tests.csproj` |
| Существующий end-to-end тест запуска | `Tests/ProgramEndToEndTests.cs` |
| Инструкции по запуску | `Tests/README.md` |

Новые тестовые классы добавлять в `Tests/`, используя пространство имён `Exchange.Tests`. При необходимости группировать их в подкаталоги по тестируемой функциональности. Не размещать тесты в основном проекте `Exchange/`.

## Написание юнит-тестов

- Использовать xUnit: `[Fact]` для отдельного сценария, `[Theory]` и `[InlineData]` для проверки одного поведения на нескольких наборах данных.
- Именовать файлы и классы как `<ТестируемыйКласс>Tests`, методы — `<МетодИлиСценарий>_<Условие>_<ОжидаемыйРезультат>`. Асинхронные методы должны возвращать `Task` и оканчиваться на `Async`.
- Строить тест по схеме Arrange / Act / Assert: подготовить данные, выполнить действие, проверить наблюдаемый результат. Проверять поведение, включая значимые ошибки и граничные случаи, а не внутреннее устройство реализации.
- Делать юнит-тесты независимыми, повторяемыми и пригодными для параллельного запуска. Не использовать реальные сетевые сервисы, базу данных, установленные клиентские программы или пользовательские настройки; внешние зависимости заменять тестовыми реализациями.
- Не изменять глобальные переменные окружения и общие файлы из параллельных тестов. Для запуска дочернего процесса передавать настройки через его `ProcessStartInfo` и отдельные тестовые файлы.
- Для необходимых файлов использовать уникальный временный каталог и гарантировать очистку ресурсов. Для ожиданий задавать таймаут; не использовать произвольные задержки как способ синхронизации.
- Следовать корневому `.editorconfig`. Не сохранять реальные пароли, токены, рабочие настройки или логи в тестовых данных и сообщениях проверок.

## Граница юнит- и end-to-end тестов

`ProgramEndToEndTests` — процессный end-to-end тест, а не изолированный юнит-тест: он запускает настоящий `Exchange.dll` с некорректным `appsettings.json`, проверяет код завершения `99` и диагностическое сообщение в stderr. Он использует собственные файлы конфигурации и завершается до управления внешними процессами.

При добавлении процессных тестов сохранять эту изоляцию, ограничивать время выполнения и освобождать ресурсы. Не запускать реальный обмен и не управлять `m_exchng.exe` без отдельно разрешённого интеграционного окружения: рабочий код может завершать все процессы с таким именем. Успешный тест ошибки запуска не подтверждает успешность обмена с внешним клиентом.

## Запуск и проверка

Запустить все тесты решения:

```powershell
dotnet test AIPractice1.slnx
```

Запустить только тестовый проект, в том числе с SDK, который не поддерживает `.slnx`:

```powershell
dotnet test Tests/Exchange.Tests.csproj
```

Запустить существующий end-to-end тест отдельно:

```powershell
dotnet test Tests/Exchange.Tests.csproj --filter "FullyQualifiedName~Exchange.Tests.ProgramEndToEndTests"
```

Для тестового проекта требуется SDK, поддерживающий `net8.0`; для решения также требуется поддержка `.slnx`. Первое выполнение `dotnet test` восстанавливает пакеты NuGet и собирает проекты.

Перед завершением изменений кода запускать `dotnet test AIPractice1.slnx` из корня и исправлять падения, вызванные изменениями. В отчёте указывать фактически выполненную команду и результат. Если проверка заблокирована, описать причину и не утверждать, что тесты прошли.
